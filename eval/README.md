# eval

วัดผลระบบด้วยชุดคำถาม ทุกครั้งที่ปรับอะไร ให้รันใหม่แล้วเทียบตัวเลข แทนการลองถามทีละข้อแล้วดูด้วยตา

| ชุดคำถาม | เอกสาร | จำนวน |
|---|---|---|
| `questions.json` | `sample-regulation-th.pdf` (ระเบียบสมมติ 7 หน้า) | 40 ข้อ |
| `questions-nu.json` | ข้อบังคับมหาวิทยาลัยนเรศวร ว่าด้วย การศึกษาระดับปริญญาตรี พ.ศ. 2559 (เอกสารจริง 11 หน้า) | 22 ข้อ |

ชุดเอกสารจริงมีคำถาม 2 แบบที่ชุดตัวอย่างไม่มี: `number_words` (เอกสารเขียนตัวเลขเป็นคำ เช่น "สิบห้าวัน") และ `partial` (เอกสารบอกแค่ว่า "ตามประกาศมหาวิทยาลัย" AI ต้องตอบส่วนที่มีโดยไม่แต่งตัวเลข) คำถามแต่ละข้อใส่ `must_not_include` ได้ ถ้าคำตอบมีคำเหล่านี้ (เช่น ตัวเลขที่เอกสารไม่ได้ระบุ) จะนับว่าผิดและขึ้นในหัวข้อ "ข้อที่ผิด" ว่าแต่งข้อมูล

## วัดอะไรบ้าง

| ตัวชี้วัด | ความหมาย |
|---|---|
| Hit@1 / Hit@3 / Hit@5 | ร้อยละของคำถามที่การค้นหาเจอหน้าที่ถูกใน 1 / 3 / 5 อันดับแรก |
| MRR | ค่าเฉลี่ยของ 1/อันดับที่เจอหน้าที่ถูก (1.0 = อันดับ 1 ทุกข้อ) |
| ตอบถูกทั้งหมด | ข้อที่มีคำตอบ: ตอบ + มีข้อมูลสำคัญครบ + อ้างอิงถูกหน้า, ข้อที่ไม่มีคำตอบ: ตอบว่าไม่พบ |
| ตอบ ไม่ปฏิเสธ | ข้อที่เอกสารมีคำตอบ แต่ AI ตอบว่าไม่พบ จะทำให้ค่านี้ลด |
| มีข้อมูลสำคัญครบ | คำตอบมีคำใน `must_include` ครบ เช่น "22" หรือ "1.50" |
| ข้อมูลต้องห้าม/แต่งขึ้น | จำนวนคำตอบที่มีคำใน `must_not_include` |
| อ้างอิงถูกหน้า | มีอ้างอิงอย่างน้อย 1 ชิ้นที่มาจากหน้าที่ถูก |
| อ้างอิงทั้งหมดที่ถูกหน้า | จากอ้างอิงทั้งหมด กี่เปอร์เซ็นต์ที่มาจากหน้าที่ถูก (ต่ำ = อ้างอิงมั่ว) |
| ตอบว่าไม่พบ | ข้อที่เอกสารไม่มีคำตอบ AI ต้องตอบว่าไม่พบ (ต่ำ = แต่งคำตอบ) |

## รัน

1. เปิด Docker, model service และ backend (frontend ไม่จำเป็น)
2. ต้องมี `sample-regulation-th.pdf` ในระบบแล้ว 1 ชุด (แนบผ่านปุ่ม + ในหน้าเว็บ) จะมีเอกสารอื่นในระบบด้วยก็ได้ เพราะตัวรันค้นเฉพาะไฟล์ที่ชุดคำถามระบุ (ดูหัวข้อถัดไป)
3. ที่ `D:\ThaiDocRAG`:

```powershell
py eval\run_eval.py
```

ไม่ต้องตั้งชื่อรอบเอง ตัวรันจะถาม backend ว่าใช้ค่าอะไรอยู่ แล้วตั้งชื่อให้ เช่น `plain-k5-v2` (รูปแบบ chunk, จำนวนชิ้น, รุ่นของ prompt) จะได้ไม่สับสนว่าไฟล์ไหนเป็นการทดลองอะไร

ใช้เวลาราว 3–4 นาที (เรียก LLM 40 ครั้ง) ไม่ต้องติดตั้งอะไรเพิ่ม ใช้แค่ไลบรารีมาตรฐานของ Python 3.10 ขึ้นไป

ตัวเลือกอื่น:

```powershell
py eval\run_eval.py --label search-only --no-chat     # วัดเฉพาะการค้น ไม่กี่วินาที
py eval\run_eval.py --label try --only q11,q12        # รันเฉพาะบางข้อ
```

ผลลัพธ์อยู่ที่ `eval/results/<วันเวลา>_<label>.md` (อ่านง่าย) และ `.json` (ใช้เทียบ) commit เก็บไว้ได้เลย เป็นหลักฐานว่าปรับแล้วดีขึ้นแค่ไหน

## ค้นจากเอกสารไหน

ไฟล์คำถามมีช่อง `"document"` บอกว่าคำถามชุดนี้มาจากเอกสารไหน ตัวรันจะหาเอกสารชื่อนั้นในระบบ แล้วส่ง id ไปกับทั้ง `/api/search` และ `/api/chat` เหมือนแนบไฟล์ในหน้าแชท ผลจึงไม่เพี้ยนเมื่อมีเอกสารอื่นในระบบด้วย และหัวไฟล์ผลจะบอกว่าค้นจากไฟล์ไหน

```powershell
py eval\run_eval.py --document "ชื่อไฟล์.pdf"                # ค้นเฉพาะไฟล์นี้แทน (ใส่ id ก็ได้ ใส่ซ้ำได้หลายไฟล์)
py eval\run_eval.py --all-documents                        # ค้นทุกเอกสาร แบบก่อนมีปุ่มแนบไฟล์ (ชื่อรอบจะมี -alldocs)
py eval\run_eval.py --questions eval\questions-nu.json      # ใช้ชุดคำถามอื่น (ชื่อรอบขึ้นต้นด้วยชื่อไฟล์คำถาม)
```

ถ้าหาเอกสารไม่เจอ ตัวรันจะหยุดและแสดงรายชื่อเอกสารที่มีในระบบ ถ้ามีไฟล์ชื่อเดียวกันหลายชุด (อัปโหลดซ้ำก่อนมีระบบตรวจไฟล์ซ้ำ) จะเตือนให้ลบชุดที่ไม่ใช้ผ่านเมนู + ในหน้าเว็บ

5 รอบในตารางด้านล่างรันตอนที่ในระบบมีแค่ไฟล์ตัวอย่าง ผลจึงเทียบกับรอบใหม่ที่ค้นเฉพาะไฟล์ตัวอย่างได้ตรงๆ

## ทดลองปรับ

ค่าที่ปรับได้โดยไม่แก้โค้ด อยู่ใน `rag-backend/.env` (แก้แล้วรีสตาร์ต backend):

| ค่า | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `CHAT_TOP_K` | 5 | จำนวน chunk ที่ส่งให้ AI อ่าน |
| `CHAT_MIN_SCORE` | 0.35 | chunk ที่คะแนนต่ำกว่านี้ไม่ส่งให้ AI |
| `CHAT_SOURCE_FORMAT` | tagged | `plain` = `[S1] ไฟล์: … หน้า …`, `tagged` = ครอบด้วย `<source id="S1" …>` |
| `CHAT_VERIFY_CITATIONS` | true | ตรวจว่าแต่ละประโยคตรงกับชิ้นไหนจริง แล้วแก้เลขอ้างอิงที่ผิดหรือขาด (ชื่อรอบจะมี `-cv`) |

ตัวอย่าง: ลอง tagged แล้วเทียบกับ baseline

```powershell
# 1. ใส่ CHAT_SOURCE_FORMAT=tagged ใน rag-backend\.env แล้วรีสตาร์ต backend
py eval\run_eval.py
py eval\compare.py eval\results\<ไฟล์รอบก่อน>.json eval\results\<ไฟล์รอบนี้>.json
```

`compare.py` บอกว่าตัวชี้วัดเปลี่ยนเท่าไร และข้อไหน "แก้ได้" หรือ "พังลง"

## ผลการทดลอง (sample-regulation-th.pdf, 40 ข้อ)

| รอบ | ตอบถูก | อ้างอิงถูกหน้า | อ้างอิงทั้งหมดที่ถูกหน้า | ข้อมูลครบ | ไม่พบถูกข้อ | เวลา LLM |
|---|---|---|---|---|---|---|
| plain-k5-v1 (baseline) | 82.5% | 82.9% | 80.6% | 94.3% | 100% | 1.64 วิ |
| tagged-k5-v1 | 80.0% | 80.0% | 84.8% | 94.3% | 100% | 1.52 วิ |
| plain-k5-v2 | 82.5% | 82.9% | 78.4% | 94.3% | 100% | 1.26 วิ |
| tagged-k5-v2 | 87.5% | 85.7% | 83.3% | 97.1% | 100% | 1.41 วิ |
| **tagged-k5-v2-cv** | **95.0%** | **97.1%** | **94.4%** | 94.3% | 100% | 1.27 วิ |

- **tagged:** ครอบแต่ละ chunk ด้วย `<source id="S1">` แก้ปัญหาโมเดลอ้างอิงเลื่อนไป 1 ชิ้น
- **prompt v2:** บังคับให้มีอ้างอิงอย่างน้อย 1 ตัว แก้ปัญหาที่ tagged ทำให้โมเดลลืมใส่อ้างอิง
- **cv (`CitationVerifier`):** ตรวจด้วยข้อความจริงว่าแต่ละประโยคมาจากชิ้นไหน แก้เลขอ้างอิงให้ 4 ข้อในรอบสุดท้าย และไม่มีข้อไหนที่แก้แล้วผิด
- **ที่ยังผิด:**
  - q13: เอกสารเขียน "สี่ปี/แปดปี" แต่คำถามใช้ "4 ปี" การค้นจึงหาหน้าที่ถูกไม่เจอ
  - q19: อ่านเงื่อนไขผิด ข้อนี้ถูกบ้างผิดบ้างในแต่ละรอบ

ทุกรอบรันครั้งเดียวบนเอกสารสมมติไฟล์เดียว ตัวเลขจึงบอกทิศทางได้ แต่ยังไม่ใช่ผลกับเอกสารจริง

## ข้อควรรู้

- **LLM ตอบไม่เหมือนเดิมทุกครั้ง:** ต่างกัน 1–2 ข้ออาจเป็นแค่ความบังเอิญ ถ้าจะสรุปว่าแบบไหนดีกว่า ให้รันแต่ละแบบ 2 รอบ
- **การตรวจ "ข้อมูลครบ" ใช้การหาคำ:** ถ้าคำตอบถูกแต่ใช้คำต่างไป (เช่น เขียน "สองภาค" แทน "2 ภาค") อาจนับผิดได้ ให้ดูส่วน "ข้อที่ผิด" ในไฟล์ `.md` ทุกครั้ง แล้วเพิ่มคำที่ใช้แทนกันได้ใน `must_include` ด้วย `|`
- **แก้ `SYSTEM_PROMPT` แล้วต้องเพิ่ม `PROMPT_VERSION`** ใน `PromptBuilder.java` ไม่อย่างนั้นผลสองรอบจะดูเหมือนใช้ prompt เดียวกัน
- **อย่าแก้ prompt ให้เข้ากับคำถามในชุดนี้โดยตรง:** เช่น อย่าใส่คำว่า "รีไทร์" ลงใน prompt ตัวเลขจะดูดีแต่ใช้กับคำถามจริงไม่ได้
